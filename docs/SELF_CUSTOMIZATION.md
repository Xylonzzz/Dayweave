# 时序：由使用者用自然语言定制

目标是让开源使用者自行提出需求，由所选模型完成开发、检查、修正和整合。DeepSeek Harness 是可替换的执行引擎，用户的定制版本不自动提交到上游，也不依赖 Codex 做最终整合。

## 页面入口

在「偏好与 AI 设置 → 定制我的工具」打开工作台，填写需求、选择 API 和自动整合或保留候选版本。可以关闭页面后继续后台任务，并在记录中查看进度、审查、测试日志及修改前后的源码。运行中可取消；候选版本可手动整合；已整合版本可恢复。服务器重启中断的任务标为已中断，不会假装继续运行。

2026-10-03 起，通过桌面启动器运行会启用版本管理：页面使用「保留候选版本 → 独立试运行 → 切换使用」，并提供恢复上一个运行版本。第一阶段仅接受兼容的前端改动；下文源码整合描述仍适用于旧的直接启动与 CLI 流程。详见 [运行版本说明](VERSION_RELEASES.md)。

默认仅已登录的本机直接连接可访问开发接口。管理员可设置 `SHIXU_DEVELOPMENT=enabled` 开放已登录远程访问，或设为 `disabled` 关闭。恢复和整合沿用源码冲突检查。离线本地空间仅显示说明，不调用开发接口。

## 环境准备与命令行

### Windows 一键准备环境

在本机进入工作台的「一键准备定制环境」，展开组件说明，勾选允许下载和准备组件后开始。当前支持 Windows x64，时序本身需已能通过 Node 24 运行；尚不是 EXE 安装器。

向导复用已有 WSL、Docker 与已配置 Harness。缺少时调用微软 WSL 安装入口（需要时请求系统授权，不自动重启），从 Docker 官方下载并校验签名后执行当前用户安装，再启动 Linux 容器。Docker 许可由用户在其窗口确认。Harness 固定到提交 `47f943859bef60e4160492346772ded9b24f765a`，源码压缩包进行 SHA-256 校验，使用固定 pnpm 11.7.0 和原始锁文件安装依赖、构建库。

工具、下载缓存、进度与日志位于 `.shixu-tools/`，不进入源码开发副本或 Git。未配置 `HARNESS_ROOT` 时自动发现向导安装的版本；已有自定义路径失效时会报告，不自动覆盖。安装程序使用独立后台进程，关闭页面不会中止；Windows 重启后再次打开时序，点击继续配置，重新检查并复用组件。完整下载会缓存，未完成下载尽量续传；若来源不支持续传，该文件需重新下载。

最终准备当前 lockfile 对应的测试镜像，并在无网络容器中验证临时文件读写和依赖加载。此步骤不调用付费模型，也不代替功能开发时的回归测试。完成后用户自行添加或选择兼容 API。

即使开放远程开发，安装接口仍只接受已登录的本机直接连接，并要求操作标识和组件安装确认。向导不自动重启 Windows、不修改 BIOS、不提供远程服务器安装和 EXE 自动更新。

### 命令行闭环

1. 运行 `npm run customize -- --doctor` 检查固定版本 Harness 和 Docker Linux 容器。
2. 将需求写进一个 UTF-8 文本文件，如 `我的需求.txt`。说明要改变的行为、保留的行为以及预期示例。
3. 执行 `npm run customize -- --request 我的需求.txt`。默认沿用时序第一个兼容 API，也可用 `--provider 接口ID` 选择。
4. DeepSeek 使用独立源码副本读取、改写文件和测试。编程结束后由宿主再次强制测试，再由独立的 DeepSeek 会话审查；审查或测试失败会反馈给开发会话，最多三轮。
5. 通过后宿主比较原始源码，未发生并发变化才自动整合，并写出文件恢复点。无需人工逐文件合并。`--review-only` 可选择仅生成候选版本。
6. 静态页面改动刷新后加载，后端改动需要重启时序。本版没有自动重启、热更新、生产健康检查或数据库迁移。

`npm run customize -- --rollback 记录ID` 恢复对应源码；如果整合后又改过同一文件，会阻止覆盖。原始副本、候选副本、模型摘要、实际测试日志、审查结论和恢复记录位于 `.shixu-development/<记录ID>/`，不进入 Git。

也可单独配置 `SHIXU_DEV_API_KEY`、`SHIXU_DEV_BASE_URL`、`SHIXU_DEV_MODEL`。密钥由宿主交给模型客户端，不交给生成代码、测试容器或模型工具。请求会发送必要源码给用户选择的模型服务，并消耗该服务额度。

## 可定制范围与验证

目前允许页面、业务模块、测试和文档的文本修改；不自动更改依赖、Harness 适配器或 development 执行控制层，不提供任意宿主 shell。只创建/替换文件，不提供删除工具。业务数据、账号、密钥、环境文件、Git 元数据不复制到开发副本。模型的“已通过”描述不能绕过程序检查。

环境构建阶段通过 Docker 拉取 Node 24 Linux 镜像并用原始 lockfile 安装依赖（禁用安装脚本）。测试阶段无外网、无个人数据，挂载源码只读，使用临时文件系统、普通用户和资源上限。固定检查包括 JS 语法、候选单元/API 测试、保留原始测试的回归检查。浏览器视觉测试、真实 API 效果、Android 实机和公开部署并不包含在此门槛中；涉及这些变化仍需对应验收，不能称为完整生产验证。

原始测试通过也不证明任何需求都正确。独立模型审查与客观测试互补；无法通过时停止，不自动覆盖现有源码。多文件整合遇到普通写入异常会恢复；进程被强制终止或断电不保证事务原子性，需根据恢复记录修复，不能把源码恢复等同于业务数据恢复。

## 后续产品界面与开源方向

- 已提供需求提交、执行进度、源码前后对照、测试结果、定制记录、独立试运行和运行版本恢复。多轮需求澄清仍待补充。
- 将主题、字段、页面排列等常见需求优先转成声明式配置；新增业务能力使用有版本的扩展接口，核心源码改造保留为进阶模式。
- 按安装环境提供执行能力：本地桌面安装运行本机开发环境；自托管服务器由管理员启用开发服务；纯离线 PWA 只使用已安装功能，无法凭浏览器启动开发容器。
- 前端兼容改动已有版本目录切换、预览端口、健康检查和启动失败恢复；后端与数据库结构变更仍需单独设计迁移与恢复协议。
- 用户定制内容与上游升级分离，记录扩展版本及兼容范围，后续升级不能静默覆盖定制。

这是自动开发闭环的第一版基础设施，尚不是任意功能均能一键上线的完整产品。
